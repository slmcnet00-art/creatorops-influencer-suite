CreatorOps 회사 OS 연동 — 2026-10-27

기본 주소: https://creatorops-suite-api.onrender.com
인증된 명세: GET /os-bridge/v1/openapi.json

인증
- 회사 OS 서버: Authorization: Bearer ${CREATOROPS_OS_API_TOKEN}
- 실행 키: 캠페인/보고서/웹훅, 기존 공개 검색/AI 생성/성과 갱신에 사용.
- /os-bridge/v1/learning 은 기존 별도 학습 조회 키 CREATOROPS_OS_TOKEN 사용.
- /admin/* 및 Gmail 승인/발송은 권한이 있는 사용자의 로그인 세션 필요.
- 실행 키를 회사 OS 브라우저에 포함하지 않음. 고정 워크스페이스만 사용.
- 실제 접속 키는 문서/Git에 넣지 않고 별도의 .local 설정 파일로 전달.

캠페인 흐름
1. GET /os-bridge/v1/capabilities: 기능과 버전.
2. GET /os-bridge/v1/brands: 브랜드 id, name, version, writable.
   writable=false는 사용자 화면에서 해당 브랜드 공유 저장을 먼저 초기화.
3. GET /os-bridge/v1/campaigns?brandId=BRAND_ID: 기존 캠페인.
4. POST /os-bridge/v1/campaigns: 생성.
   If-Match: 브랜드 version
   Idempotency-Key: 회사 OS의 작업별 고유 키 (최대 160자)
   {"brandId":"BRAND_ID","campaign":{"name":"일본 클렌징 캠페인","campaignType":"제안형","contentFormats":["숏폼"],"targetMarkets":["JP"],"budget":5000000,"targetViews":100000}}
   새 생성 201; 같은 키/같은 입력 재요청은 200 duplicate=true.
   같은 키/다른 입력은 409. 전송 오류 시 같은 키와 입력으로 재요청.
5. GET /os-bridge/v1/campaigns/CAMPAIGN_ID?brandId=BRAND_ID: campaign, version 및 ETag.
6. PATCH /os-bridge/v1/campaigns/CAMPAIGN_ID: 수정.
   If-Match: 최신 브랜드 version
   {"brandId":"BRAND_ID","campaign":{"name":"수정한 이름"}}
   응답의 version을 다음 쓰기에 사용. 버전은 브랜드 전체 스냅샷 단위.
   409는 최신 내용을 읽고 병합 검토, 428은 If-Match 누락.
- 계획 조건/목표/일정/상태/다중 콘텐츠 형식/운영 국가를 수정.
- 실제 매출/집행/진행률/크리에이터 배정 필드 직접 쓰기는 차단.
- 캠페인 삭제/신규 브랜드 생성은 제공하지 않음.
- 기존 검색/AI 응답 계약 유지. 생성 결과를 캠페인에 자동 저장하지 않음.
- campaign.outputLanguage: ko/en/ja/zh/zh-CN.
- 성공 대부분 {data:...}, 오류 {error,message}. 학습 pack과 OpenAPI는 최상위 객체.

- 공개 HTTPS/443, 사용자정보/쿼리/fragment 없는 URL. 리다이렉트 미지원.
- 실제 수신 주소를 제공받지 않아 구독은 자동 활성화하지 않음.
- 등록 후 발생 이벤트부터 발송, 소급 발송 없음. 비활성화는 enabled=false.
- 본문 id,type,workspaceId,occurredAt,data. 참조 ID/상태/버전만 포함.
- 업무 저장 후 큐 저장에 실패하면 캠페인 응답 webhook.queued=false 확인 필요.
- 큐는 DB 유지, 30초 간격 처리, 최대 5회 시도.
- at-least-once이므로 동일 이벤트 재수신 가능. 수신자는 event.id로 중복 제거.
- 주소 변경 시 이전 주소용 이벤트를 새 주소로 보내지 않음.
- 처리 성공은 2xx 응답. GET /os-bridge/v1/webhook/deliveries 로 최근 100건 확인.

판단 메모리 (2026-10-27)
관리자 > LLM Ops > 피드백 · 판단 사례 · 운영 원칙에서 관리한다.
일반화된 피드백 / 판단 이유·결과 / 원칙 후보를 함께 저장하고 별도 승인한다.
원칙은 해당 워크스페이스 전체 브랜드에 공통이며 기능별로만 적용한다. 브랜드 전용 전략, 개인정보, 원본 메시지, YouTube 통계는 입력하지 않는다.
승인 전·반려·중지 사례는 모델에 전달하지 않는다. 관리자 정책·법적 의무·현재 캠페인 브리프를 우선한다.
다음 전략·추천·가이드·섭외 문구 서버 AI 호출에서 승인 원칙을 참고하며, 이미 생성된 결과나 발송 내용은 변경하지 않는다. 외부 회사 OS의 자체 모델 실행이나 정적 템플릿에는 자동 주입되지 않는다.
LLM 호출 상세의 decisionMemory에는 revision, rules[{caseId,version}]가 남는다. 실제 전달한 원칙은 암호화 입력에 저장되고 기존 30일 보존 정책을 따른다.
실패 재시도는 당시 입력·원칙을 유지한다. 최신 원칙을 다시 붙이지 않는다.
잘못된 원칙은 중지한다. 수정은 새 사례로 제안하고 기존 원칙을 중지한 뒤 새 원칙을 승인한다. 이전 원칙 재승인으로 되돌릴 수 있다. 같은 기능·주제의 중복 승인은 거부한다.
누적 사례는 workspaces.settings.decisionMemoryVault에 AES-256-GCM으로 암호화한다. 기존 LLM_OPS_ENCRYPTION_KEY 보존이 필요하다. 일반 회원에게 원문을 노출하지 않는다. 사례 200개, 기능별 승인 20개, 사례별 검토 이력 100개 한도 초과는 명시적으로 거부한다.
이는 모델 가중치 재학습이나 자동 성과 개선 판정이 아니다. 판단 결과는 관리자가 입력·검토한다.

관리자 API (기존 Owner/Admin Bearer 인증만 허용, OS 서비스 키 불가)
GET /admin/decision-memory -> {data:{revision,cases}}
POST /admin/decision-memory -> {revision,featureKey,topic,feedback,judgment,principle,runId?}; 201 {data:{revision,cases}}
featureKey: campaign-strategy | creator-recommendation | content-guide | outreach-message
POST /admin/decision-memory/:id/review -> {revision,action:approve|reject|retire}; 200 {data:{revision,cases}}
오래된 revision은 409. 잘못된 입력/호출 연결은 400. 호출 연결은 같은 워크스페이스·기능만 허용. 수정 후 새 revision으로 다음 작업을 보낸다.
